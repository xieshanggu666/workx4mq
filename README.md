# 🎲 营销活动抽奖与积分运营平台（多租户版）

基于 **Vue 3 + Vite + Pinia** 的营销运营平台，覆盖抽奖玩法、积分体系与运营管理全链路：
**多租户组织、RBAC 细粒度权限、租户数据强隔离、全链路审计**，以及多玩法抽奖、加权随机、
积分任务、积分商城、风控审核与申诉、实物物流、售后闭环、**奖品采购入库（审批 + 分批验收 + 验收差异）**、
**供应商账单结算（运营拟单 → 财务复核 → 结算付款，按采购批次与售后补发回写库存对账）**、
**营销预算与成本控制闭环（按租户/活动设预算，抽奖成本/积分奖励/采购入库/供应商结算实时占用并支持财务审批）**、
卡券账户与核销、七类口径业务对账。
纯前端零后端即可浏览运行。

## 功能特性

- **多租户组织与权限中心**：平台方 + 多个入驻组织（租户）；活动/商品/库存/单据/卡券/流水/对账/审计全部带 `tenantId` 物理标记，员工仅可访问归属租户，平台超管可跨租户巡检与开通/停用租户；客户（消费者）可切换"逛店"上下文
- **RBAC 细粒度角色**：内置组织管理员/活动运营/风控专员/物流客服/财务对账/客服只读 6 个角色，支持租户自定义角色与按权限位勾选；写操作在 store 层统一做「权限校验 + 租户归属校验」，越权与停用账号登录一律拒绝并写 `result=denied` 审计
- **全链路审计**：登录/越权、组织与权限变更、活动、积分、风控、物流、售后、卡券、对账统一审计日志；每次用户操作生成 `traceId`，级联的积分流水/卡券台账/审计共享同一追踪号，可在「全链路审计」按租户/模块/结果/关键词检索并还原链路时间线，支持导出 JSON
- **多租户联动**：看板、风控队列、发货/售后队列、卡券核销、积分流水、库存与六类对账口径全部按当前租户上下文独立计算，一租户一业务日一张差异单，跨租户券码核销被拦截
- **多玩法抽奖**
  - 🎡 幸运转盘（SVG 扇形 + 旋转动画）与 🎰 刮刮乐（Canvas 刮涂层揭晓）
  - 加权随机抽取、奖品库存扣减、积分奖品自动入账
- **抽奖任务自动结算**：任务进度按真实参与记录累计（正常 + 审核放行计入；风控冻结暂缓、撤销不计），达标自动发奖并同步积分流水；风控放行后按记录归属业务日补计、撤销后确认回退；任务进度与领奖记录按业务日归档台账，跨日审核不串账、不重复发奖
- **风控校验**：每日限抽 / 累计限抽 / 奖品库存余量 / 积分不足拦截
- **风控申诉**：抽奖与兑换命中可配置规则时生成风险审核单，冻结相关积分、预占奖品/商品库存；用户可申诉，运营审核后放行（发奖/核销）或撤销（返还积分/库存/次数）；角色权限 + 全量操作记录，状态机保证幂等防重复扣减
- **积分库存对账**：按业务日核对抽奖成本/中奖积分、兑换扣减/撤销返还、任务奖励与积分流水、风控冻结、奖品/商品库存，生成可追溯差异单（P1 积分发生额 / P2 任务台账逐笔 / P3 余额链 / P4 冻结单据 / P5 库存账实）；运营复核后仅以 append-only 补偿流水与库存调整凭证修正，保留全部原始记录；积分流水作为历史对账、余额链与奖励统计底账不裁剪，差异签名幂等防重复执行/重复补偿，任务发奖与补偿统一按领奖台账 id 勾稽，跨日审核与补偿按业务日归属、实际处理日单独留痕，余额、库存、看板即时同步
- **积分体系**：签到与任务赚积分、积分明细流水（含冻结/返还/放行/任务结算/对账补偿标记）、积分商城兑换
- **实物收货发货**：中奖或兑换的**实物奖品/商品**自动生成发货单，用户填写/修改收货信息（姓名、手机号、地区、详细地址），运营接单并录入快递公司/单号发货，用户查看物流后确认收货；状态机 `待填地址 → 待发货 → 已发货 → 已收货（/已退回）`，冻结/撤销的风控单不产生发货单，全部操作留痕
- **物流轨迹与售后闭环**：运营发货后生成揽收节点，用户/运营可同步快递轨迹（揽收→干线→派送→签收，幂等推进）；用户对已发货/已收货订单申请**拒收、退货或补发**，运营审核通过后统一回写——拒收/退货：库存回补 + 积分返还（append-only 退款流水）+ 发货单退回；补发：库存扣减 + 生成补发发货单（沿用原地址）；驳回不动账。**补发缺货时售后单不驳回、整单挂起「待补货」（不落账），运营发起采购、验收入库后可从待处理售后继续履约**。售后退款/退回/补发纳入对账 P1 积分发生额与 P5 库存账实勾稽，库存不足等异常整体回退不落账，申请/审核/同步全量权限留痕
- **奖品采购入库与验收差异**：运营按**活动奖品/商城商品**发起采购单（数量/供应商/协议单价/事由，可从待补货售后单一键发起并回指售后单），**审批后仓配分批验收入库**——状态机 `待审批 → 已审批待入库 → 分批验收中 → 入库完成 / 验收差异结案`（另可驳回/审批前撤销），三权分立 RBAC（活动运营 `purchase:apply` / 财务 `purchase:approve` / 物流客服 `purchase:inbound`）；验收按批次登记**到货量 / 合格入库量 / 验退拒收（破损不合格不入库）/ 到货短少（供应商确认少发不再补发→提前结案）**，仅合格量抬升 SKU 的 remain/stock，差异写入 append-only 验收差异台账；P5 库存对账以「初始 + 采购入库 − 有效消耗 + 调整」勾稽，正常入库不产生调整凭证
- **供应商结算与采购对账闭环**：入库完成（或差异结案）后，运营按采购单发起**供应商账单（结算单）**，按实收合格量 × 协议单价计价，状态机 `待提交 → 财务复核中 →（驳回可修订重提）复核通过待结算 → 已结算`，三权分立（活动运营 `supplier:bill` / 财务 `supplier:review` + `supplier:settle`）；**按采购批次逐批勾稽**到货/合格/验退/短少，关联缺货补发的采购单在售后补发履约完成后，复核/结算自动勾稽出**补发占用件并扣减货款（不重复计价、不重复入库）**；结算时回写库存对账快照（reconWriteback）并回写采购单，账单/差异/快照全部 append-only 随 WAL 恢复。新增 **P7 采购结算对账**（独立于 P1–P6，不计入积分库存差异 openCount），实时检出未拟单/待复核/待结算/补发未履约/金额过期等未闭环项
- **营销预算与成本控制闭环（💰 预算成本）**：
  - **预算编制与财务审批**：按「租户级 / 活动级」两级 ×「积分 / 资金」双币种设预算（一口径一币种同时仅一张生效/待审批预算）；活动运营 `budget:manage` 编制与申请追加/调减，财务 `budget:approve` 审批生效/驳回、冻结/解冻/关闭；调整走审批流并 append-only 留痕。
  - **四类成本实时占用**：① 抽奖积分成本与积分奖品奖励（正常落账 settle；风控冻结先 reserve 预占，放行核销、撤销释放）；② 兑换积分成本与任务积分奖励；③ 采购申请按「数量 × 协议单价」reserve 预占资金预算（审批驳回/申请人撤销 release，审批通过不抬库存也不改占用）；④ 供应商结算付款核销采购预占并按账单应付 settle 为实际资金成本；售后退货返还积分时 refund 冲回预算成本，缺货补发件随关联采购结算核销（不重复计价）。
  - **超额/冻结整笔阻断**：业务落账前预算预检 + 服务端业务锁内二次核验（同笔业务多成本项按预算汇总校验），超预算或预算冻结时抽奖/兑换/采购整笔阻断（积分库存不产生半截变动），并发不超预算；占用进度 80% 预警、超支红条提示。
  - **台账与审计**：`budgetLedger` append-only 记录 reserve/settle/release/refund（业务凭证、品类、金额、操作人、traceId），按 effectId 幂等、随 WAL 重放恢复；预算看板统计待审批/超支/预警与积分、资金累计占用，全部动作归入「预算成本」审计模块。
- **卡券账户与核销**：中奖或兑换**券类奖品/商品**（满减券/代金券/兑换券）自动发券至卡券账户，一券一全局唯一券码；风控命中时只**预占**券库存（不发券），放行后**交付**发券（有效期自放行日起算）、撤销则**释放**预占（券始终不发出）。用户在「🎟️ 卡券核销」出示/复制券码，运营扫码或输码核销，状态机拦截重复核销与到期核销；按业务动作做卡券到期扫描（到期自动失效），发放/预占/交付/核销/到期/补券全部写入 append-only 卡券台账。对账新增 **P6 卡券账户勾稽**（有效券记录发券、券码唯一、核销信息、到期状态），漏发可按差异单补发新券（新券码、有效期自补券日起算，append-only 不伪造历史），孤立券/重复码人工核查；券库存仍由 P5 统一勾稽，看板/Tab 角标同步
- **运营侧**：运营看板（累计抽奖、参与人数、中奖统计、库存、待风控/冻结积分、任务结算量、对账业务日/待复核/补偿统计、实物发货各状态单量、售后待审核/待补货/已完成/补发单量、**采购待审批/待入库/入库完成/累计验收件数**、**预算待审批/生效/超支/预警/积分与资金累计占用**、卡券发放/待核销/已核销/过期/预占）、活动管理（新建 / 暂停 / 重置库存 / 删除）
- **演示友好**：内置两个租户——星河商贸全套业务种子（含预算单与历史占用快照：租户/活动两级积分与资金预算、待审批与已关闭预算）+ 云雀数科独立活动/商品/卡券/风控/物流/预算种子；预置用户积分、风控审核单（待审/已申诉/已放行/已撤销/跨日待审）、历史业务日任务台账与一笔历史漏记差异、卡券账户、物流与售后种子；组织内含各角色成员与一名离职停用成员，平台方含超管账号；纯前端零后端即可浏览运行

## 多租户与权限模型

| 角色 | 关键权限 | 数据范围 |
| --- | --- | --- |
| 平台超级管理员（m-platform） | 全部权限 + `tenant:manage`（开通/停用/配置租户） | 跨全部租户巡检，不直接做单租户业务 |
| 组织管理员（org_admin） | 除租户管理外的全部本租户权限 | 仅归属租户 |
| 活动运营（ops_activity） | 活动管理、积分台账查看、**发起采购申请/供应商账单**、物流轨迹 | 仅归属租户 |
| 风控专员（risk_analyst） | 风控审核、规则配置、积分台账 | 仅归属租户 |
| 物流客服（logistics_clerk） | 接单发货、轨迹同步、售后审核、**分批验收入库（登记验收差异）** | 仅归属租户 |
| 财务对账（finance_auditor） | 卡券核销、对账执行/复核/补偿、**采购审批、供应商账单复核与结算**、审计查看 | 仅归属租户 |
| 客服只读（service_readonly） | 积分台账查看、轨迹同步 | 仅归属租户 |
| 消费者（客户） | 抽奖/兑换/申诉/收货/售后/出示券码 | 各租户内仅本人数据，可切换"逛店" |

- **强隔离**：活动/奖品/商品/库存、业务记录、审核单、发货单、售后单、卡券实例与台账、积分流水、任务台账、差异单、库存校正、审计日志均带 `tenantId`；查询 getter 与对账计算强制按当前数据上下文过滤，写操作在 store 层再次校验归属
- **拒绝留痕**：权限不足、跨租户访问、停用账号登录统一经 `deny()` 处理：toast 拦截、业务数据零变更，并写 `result=denied` 审计（含操作人、IP、渠道、租户、traceId）
- **演示身份切换**：顶栏可切换租户上下文；「🏢 组织权限」中心可一键登录任意成员（含停用账号，触发拒绝留痕）；各业务页保留的"用户/运营"视角按钮在运营档自动登录当前租户组织管理员
- **全链路审计**：审计日志 append-only，字段含动作/模块、操作人（员工带租户前缀）、身份类型、成员 id、租户、`traceId`、渠道、IP、结果、明细与时间；一次顶层操作（抽奖/兑换/审核/发货/售后/核销/对账补偿等）与其级联流水、卡券台账、库存凭证共享 traceId，点击链路号可时间正序还原；检索维度为租户/模块/结果/操作人/关键词，可导出当前筛选 JSON

### 联机模式（前端接入服务端 API）

```bash
npm run server            # 终端 1：履约服务端（WAL 事件库，默认 :8080）
npm run dev               # 终端 2：前端（/api 经 vite 代理到 :8080）
# 顶栏徽标变为「🌐 服务端联机」即已接入；未检测到服务端时保持「📴 本地离线」
```

- **写操作全部走服务端**：活动、积分、库存、风控、物流、采购、供应商结算、预算、卡券、对账等 41 个 store 动作在联机后统一改走 REST API，本地不再落账；每次写后由 `GET /api/bootstrap` 全量水合服务端 WAL 投影（多客户端并发看到同一真实源）。
- **统一租户权限**：会话 token（`Authorization: Bearer`）随请求下发，RBAC 权限位 + tenantId 归属在服务端强制校验；越权/停用/跨租户写 `result=denied` 审计并同步到前端 `lastDenied`。
- **幂等**：客户端为每笔写自动生成 `idempotencyKey`（双击/重试/断网重发由服务端 idem 表去重）；积分流水 `(kind,refId)`、库存/预算 `effectId` 兜底。
- **并发**：服务端 `KeyedLock` 按键互斥（积分户/商品/活动/预算），锁内二次校验，并发不超卖、不超预算。
- **WAL 恢复**：写前日志 + 状态投影 + Saga `processing` 锚点，崩溃重启自动续办到终态；前端业务日以服务端业务时钟为准。
- **离线快照迁移**：离线模式下全部本地变更防抖持久化到 localStorage（断网/刷新可续跑）；恢复联机后顶栏出现「⬆️ 迁移离线快照」，平台超管一键把本地台账快照经 `POST /api/migration/run` 校验并重建上链（行级固定 id + 批次 manifest 幂等，重跑零增量；已有业务数据的服务端拒绝新批次，防双计）。迁移目标库用 `npm run server:fresh`（`--no-seed`，仅组织/权限种子）启动。

## 服务端履约链路（交易 · 积分 · 库存 · 风控协作）

抽奖/兑现已从纯前端升级为**真正的服务端协作链路**（`server/`，纯 Node 内置模块、零第三方运行时依赖、WAL 事件持久化）：

```bash
npm run server            # node server/index.js --port 8080 --db data/server-wal.jsonl
npm run server:fresh      # 迁移目标库模式（--no-seed：仅组织/权限种子，等待离线快照迁移导入）
npm run test:server       # 服务内核：并发不超卖 / 幂等 / 崩溃续办 / 跨日审核 / P1–P6 对账补偿 / RBAC / 采购入库 / 供应商结算闭环
npm run test:migration    # 历史台账迁移：校验 → 迁移 → 对账补偿 → 重跑幂等
npm run test:http         # HTTP E2E：真实起服，token 鉴权 / REST / 采购+供应商结算 API / 故障注入重启续办
npm run test:front-server # 前端↔服务端联机：真实 store 经 API 全链路（水合/幂等/RBAC/跨租户/预算/并发/WAL 重启/离线快照迁移/降级）
```

### 架构与关键设计

```
server/
├── index.js               # 入口（node:http）
```

- **统一扣分预占与发奖幂等补偿**：客户端 `idempotencyKey` 整笔交易去重；每个积分流水带 `(kind, refId)`、每笔库存变动带 `effectId`，WAL 重放与 Saga 续办绝不产生第二次扣分/扣库存/发奖。
- **多用户并发**：`points:<userId>`、`goods:<id>`、`act:<activityId>` 按键互斥（多键有序加锁防死锁），库存余量在锁内二次确认；10 并发抢 3 件恰好成交 3 笔，余额/库存/流水精确一致。
- **故障续办**：交易与审核单带 `processing` 锚点 + 分阶段 `stages`；注入 `draw.afterCost / release.afterConsume / revoke.afterRefund` 等崩溃点后，进程重启重放 WAL 并自动把中断的 Saga 续办到终态（`POST /api/admin/resume` 可手工触发）。
- **跨日审核**：可写虚拟业务时钟（`POST /api/admin/day`）；冻结权益跨日保留，放行后积分奖品/任务奖励流水 `bizDate=原参与日`、`date=实际处理日`，对账不串当日。
- **历史台账迁移**：迁移前校验余额链/库存账实/冻结单/券码唯一，不通过整批拒绝；通过后以**固定行 id + 固定 effectId** 重建事件库（中断重跑零增量），旧种子日期按 ts 反推业务日、补期初结转行与冗余成本字段；manifest 记 sha256 校验和；迁移后历史漏记直接由 P1/P2 检出并走同一套补偿链路。
- **租户鉴权/对账/审计贯通**：登录换 token，写接口强制 RBAC + tenantId 归属，越权/停用登录写 `result=denied` 审计；一租户一业务日一张差异单；一次操作的积分流水、卡券台账、审计共享 `traceId`。

## 抽奖任务自动结算说明

- **进度来源**：抽奖任务（如「今日抽奖3次」）进度唯一来源于真实参与记录——状态为 `正常` 与 `已放行` 的抽奖记录计入；`冻结` 暂缓计入，`撤销` 不计入。无手动领取入口，杜绝刷任务与重复发奖。
- **自动结算**：每次有效参与落账后按归属业务日结算，达标即自动发放奖励并写入积分流水（`任务结算：xxx`）；同一（任务 × 业务日）仅发奖一次（`taskClaims` 台账判重），发奖流水记录台账 `refId`，重复触发、历史流水留存检查与对账补偿均以此统一幂等跳过。
- **风控联动**
  - 冻结：该笔暂缓计入，任务页与审核单均提示"审核中暂缓"；
  - 放行：按参与记录的**归属业务日**补计进度，若达标自动补发奖励（流水与台账标注"跨日补计"），不计入审核当日，避免跨日串账；
  - 撤销：该笔确认不计入（冻结期未计入，撤销后自然回退），积分/库存/限次按既有规则返还。
- **按业务日归档**：积分中心「任务结算记录」按业务日分册展示每日进度、审核中笔数与领奖记录（含归属日/发放日）；业务日切换时先兜底结算上一日再归档，历史台账保留不丢。
- **同步积分流水**：任务奖励实时入账并写 append-only 流水；跨日补计的流水日期为实际发放日、备注归属业务日，保证账实一致。
- 逻辑冒烟测试：`npm run test:settle`（覆盖进度累计/冻结暂缓/放行补计/撤销回退/幂等防重/跨日隔离）。

## 积分库存对账说明

- **对账口径（按业务日）**
  - **P1 积分发生额**：由业务记录逐笔推导应有净额——抽奖成本（落账即扣）、中奖积分（正常按参与日 / 放行按原参与日归属）、兑换扣减、撤销返还（按审核日）、任务奖励（含跨日补计，按归属业务日）——与积分流水实际净额勾稽，补偿流水单列；
  - **P2 任务奖励台账**：`taskClaims` 每笔领奖必须有对应流水，原始发奖流与 `task-comp` 补偿流均按台账 id 精确勾稽（旧种子无 id 时按任务名+金额+业务日兜底）；
  - **P3 余额链**：append-only 流水的余额快照按时间重放必须逐笔连续，最新一行余额 == 当前可用积分；
  - **P4 风控冻结单据**：在审单（pending/appealed）与业务记录状态一致、冻结积分=业务成本、预占库存=奖品/商品账面 frozen；
  - **P5 库存账实**：应有 remain = 初始库存 + 采购验收入库（按批次实收）− 有效消耗（revoked 不计）+ 库存调整凭证，逐 SKU（奖品按活动维度、商品按 goodsId）比对。
  - **P6 卡券账户**：有效券业务记录（normal/released 带 couponId）必须有券实例（漏发可补）；券实例必须回指一条有效业务记录（孤立券人工核查）；券码全局唯一（重复码人工核查）；已核销券必有核销人/时间；已过到期时刻仍 available 的券可自动补做到期。券库存（券奖品/券商品）仍由 P5 统一账实勾稽，发券/核销/补券/采购入库不重复扣库存。
- **可追溯差异单**：一业务日一张单，保存首次快照、差异指纹签名、每次执行人/时间/结果、复核人与备注、全部补偿凭证；重复执行签名不变即同一版本，只追加执行痕迹。
- **复核后补偿（只追加，不改原始记录）**
  - 任务缺笔：按台账逐笔补记 `task-comp` 补偿流水并同步余额，按台账 id 幂等；若原始发奖流水仍存在则不补；
  - 积分净额少记（残差>0）：补记 `recon-comp` 流水；长款/多记（残差<0）不自动扣减，标记人工核查；
  - 库存盘亏/盘盈：不凭空回补或扣减实物，登记 -diff 的库存调整凭证把账面核销/补登到实物，保留调整前后快照；
  - 卡券漏发：按有效业务记录补发**新券**（新券码、有效期自补券日起算、券带「对账补券」标记并回指原业务记录），按 recordId 幂等不重复发；到期未流转补做 expired；孤立券/重复码/核销信息缺失只标记人工核查，不自动作废或改码；
  - 冻结单据不一致：引导至「风控申诉」处理，不自动核销预占。
- **跨日审核/补偿**：流水带 `bizDate`（归属业务日）与 `date`（实际处理日），任务/奖品跨日放行计入原业务日对账、不串当日账；补偿流水续在余额链末端保证快照链连续。历史流水完整留存，不按演示条数裁剪，避免历史净额、余额快照与领奖台账失去勾稽。
- **权限与同步**：仅运营可复核/补偿（用户视角只读）；补偿后余额、奖品/商品库存、运营看板、Tab 角标即时同步，补偿流水在积分中心带「对账补记/对账补偿」标记与归属日。
- 演示注入：对账页运营视角可注入「任务奖励漏记 +30」「商品盘亏 1 件」「卡券漏发 1 张」；种子另在上一业务日预置一笔 5 积分历史漏记，可完整走 对账 → 复核 → 补偿 → 再对账平账 闭环。
- 逻辑冒烟测试：`npm run test:recon`（覆盖六类口径检出、权限拦截、跨日补偿归属、流水留存、幂等防重、余额链自愈、库存核销、卡券 P6 检出/补发、看板同步、原始记录保留）。

## 实物收货发货说明

- **适用范围**：奖品与商品带 `physical` 标记（积分奖品/券卡/优惠券为虚拟，直接到账；其余实物走物流）。实物在中奖或兑换**成功后**才生成发货单。
- **状态机**：`待填地址 pending_address → 待发货 to_ship → 已发货 shipped → 已收货 received`；售后拒收/退货审核通过后进入终态 `已退回 returned`（详见「物流轨迹与售后闭环说明」）
  - 用户中奖/兑换实物：自动生成「待填地址」发货单，在「📦 物流发货」填写收货人、手机号（11 位校验）、所在地区、详细地址；发货前允许修改；
  - 运营接单发货：「待发货」队列中查看收件信息，录入快递公司与快递单号（可选备注）后发货，物流信息对用户可见；
  - 用户确认收货：已发货订单一键确认收货，订单闭环。
- **风控联动**：命中风控的实物单**冻结期间不产生发货单**（库存仅预占、奖品未发放）；运营放行后才补发发货单；撤销则业务作废、库存/积分返还，始终无发货单。
- **权限与幂等**：用户只能填写/修改本人地址、确认本人订单；仅运营可接单发货；状态机保证不可跨状态操作、不可重复发货/重复收货；生成、填地址、发货、收货全部写入操作记录。
- **演示数据**：预置一笔已发货待确认的「500元购物卡」与一笔待填地址的「定制帆布袋」兑换；Tab 角标按视角提示（用户：待填地址+待收货；运营：待发货+待审核售后）。
- 逻辑冒烟测试：`npm run test:ship`（覆盖状态推进/表单校验/权限隔离/幂等防重/风控冻结-撤销-放行联动/审计留痕/对账仍平衡）。

## 物流轨迹与售后闭环说明

- **物流轨迹同步**：运营发货即生成「已揽收」节点；用户与运营均可在发货单上「同步物流」，按 揽收 → 干线运输 → 派送 → 签收 逐节点推进（演示环境每次同步推进一步，幂等防重复追加；已到签收终态不再推进）。用户确认收货时若轨迹未同步到签收，自动补齐终态节点；售后退回/补发受理也会追加对应节点。轨迹 append-only 挂在发货单上，双视角可见。
- **售后申请（用户）**：按发货单状态开放入口——已发货可申请**拒收**/**补发**，已收货可申请**退货**/**补发**；原因必填。同一发货单已有待审核售后单时幂等拦截，同类型已完成的售后不可重复申请（驳回后可重新提交）。
- **售后审核（运营）与回写**：状态机 `待审核 pending → 已完成 done / 已驳回 dismissed`
  - **拒收/退货通过**：库存回补 1 件、按申请时快照返还积分（兑换成本/抽奖参与成本，免费奖品为 0 则不写流水）、发货单 → `已退回` 并追加退回轨迹节点；
  - **补发通过**：库存再扣 1 件、生成补发发货单（沿用原收货信息直接进入待发货队列，关联原单与售后单），原单追加补发受理节点；不退款；
  - **驳回**：仅留痕，积分/库存/发货单均不变动。
- **异常回退**：审核通过前统一校验（库存目标存在、补发库存余量），任一不满足则整体拦截不落账。**补发缺货（remain=0）不再直接报错：售后单转 `waiting_stock` 待补货挂起（同样不落账），运营发起采购并验收入库后，可从「待处理售后」继续补发履约**（采购首批有余量即可，无需等采购入完）。
- **对账台账勾稽**：售后退款计入 **P1 积分发生额**（按审核日归属，与 refund 流水勾稽，退款流水带 `refId/refType=after-sale` 回指售后单）；售后退回/补发计入 **P5 库存账实**（有效消耗 = 业务消耗 − 已退回 + 已补发，差异单行内展示售后修正）；跨日售后按审核日入账，不串申请日账。采购入库按验收批次计入 P5 账面总量。
- **权限与留痕**：用户仅能对本人发货单申请售后、查询本人物流；仅运营可审核售后；申请/通过/驳回/轨迹同步全部写入操作记录，售后单 append-only 保留快照（退款额、库存定位、审核人/时间/备注）。
- **演示数据**：昨日一笔「盲盒福袋」退货已完成（积分 +200 已返还、库存已回补、发货单已退回，昨日对账两侧勾稽）；今日一笔「定制帆布袋」补发申请待审核（运营视角物流页可审）；另有一笔「限量联名公仔」补发因缺货挂起「待补货」（采购单首批 6 件已验收入库，可继续履约，见「奖品采购入库说明」）；已发货的「500元购物卡」轨迹已同步至派送中，可继续同步或确认收货后申请售后。
- 逻辑冒烟测试：`npm run test:aftersale`（覆盖轨迹推进/终态幂等、申请权限与状态机、缺货挂起 waiting_stock、采购入库后继续履约、驳回不动账、拒收/退货/补发回写、P1/P5 对账勾稽、跨日归属、审计留痕）。

## 奖品采购入库说明

- **适用范围**：活动奖品与商城商品 SKU 均可发起采购（券类/积分类虚拟 SKU 同样可补，采购只动库存账面、不涉及物流）。
- **采购单状态机**：`待审批 pending → 已审批待入库 approved → 分批验收中 receiving → 入库完成 received`；终态另含 `已驳回 rejected`（审批不动库存）与 `已撤销 canceled`（仅 pending 态、发起人本人或管理员可撤）。审批通过本身不抬库存，**库存只在实际验收批次时按实收增加**。
- **三权分立（RBAC）**：活动运营/自定义角色持 `purchase:apply` 发起采购；财务对账持 `purchase:approve` 审批；物流客服持 `purchase:inbound` 分批验收入库；组织管理员隐式拥有全部三项，平台超管可跨租户查看但不直接处理租户单据。所有写操作强制租户归属校验，越权/无权写 `result=denied` 审计。
- **分批验收**：一张采购单可分多批入库，每批录入实收数量（可带供应商/承运方与验收备注），累计实收不得超过审批数量（超量整笔拦截）；全部入满自动转「入库完成」并记录完结时间，之后重复验收被状态机幂等拦截。每批追加 **append-only 验收批次台账**（采购单 id、批次前后 remain/stock 快照、验收人、时间、traceId）。
- **库存口径**：验收通过即 `remain += 实收`、`stock += 实收`（账面总量随采购抬升，而非凭空调整）；P5 库存账实以 `初始库存 + 采购入库 − 有效消耗（含售后退回/补发修正） + 对账调整` 勾稽，正常采购入库**不产生库存调整凭证**（区别于盘亏/盘盈的对账补偿）。
- **缺货补发继续履约**：售后补发审核通过时若目标 SKU `remain=0`，售后单不再被驳回，而是转为 `待补货 waiting_stock`（库存/积分/发货单均不变动，仅留痕）；运营可从该待处理售后单一键发起关联采购单，审批并验收入库后——**首批有余量即可，不必等采购入完**——在物流页待补货队列（或采购页待处理卡片）点「继续补发履约」，按原审核口径扣库存、生成补发发货单，售后单转已完成。同一发货单有待处理（待审核/待补货）售后时禁止重复申请。
- **看板与留痕**：采购 Tab 角标 = 待审批 + 待入库；物流 Tab 运营角标含待补货售后；运营看板新增采购待审批/待入库/入库完成/累计验收件数与售后待补货统计。`purchase-apply/approve/reject/cancel/inbound` 与 `aftersale-shortage/resume-ready` 全部写入「采购入库」「售后闭环」模块审计，验收批次共享操作 traceId。
- **演示数据**：星河商贸预置三张采购单——保温杯 ×50（已分两批 30+20 验收入库）、限量联名公仔 ×10（审批通过、首批 6 件验收中，关联一笔缺货挂起的补发售后，剩余 4 件待验收入库）、iPhone 16 ×2（待财务/管理员审批）；限量公仔初始 2 件已兑完并签收，第二笔补发申请正挂起在「待补货」队列。
- 逻辑冒烟测试：`npm run test:purchase`（覆盖三权分立、状态机、驳回/撤销、分批超量/重复拦截、入库抬 remain/stock 与批次台账、缺货挂起→采购→继续补发、P5 平账无需调整凭证、租户隔离、审计留痕）。

## 卡券账户与核销说明

- **券类范围**：奖品与商品带 `couponId`（券模板定义在 `src/mock/data.js` 的 `COUPONS`）即为券类——满减券（门槛+减免）/ 代金券（面值）/ 兑换券（权益文案）。券类走卡券核销，与实物物流互斥；积分奖品等其余虚拟权益仍直接到账。券库存挂在奖品/商品的 stock/remain/frozen 上，与实物共用 P5 库存勾稽。
- **发券与风控联动（三态）**
  - 中奖/兑换正常落账：自动发券至用户卡券账户，生成全局唯一券码（`CP-XXXXX-XXXXX`），有效期自发券日起 `validityDays` 天（到期日 23:59 前可核销）；
  - 风控冻结：券库存 `remain-1 / frozen+1` **预占**，但**不生成券实例**（券码未发放），用户卡券页可见「预占待交付」提示；
  - 运营**放行**：核销预占库存并**交付发券**（有效期自**放行日**重新起算，写 `deliver` 台账）；运营**撤销**：库存回补、预占**释放**，券始终不存在（写 `revoke` 台账）。
- **用户出示 / 运营核销**
  - 用户在「🎟️ 卡券核销」查看卡券（待核销/已核销/已过期筛选）、复制券码到店出示；
  - 运营在扫码/输码工作台输入券码核销：券码自动归一化（忽略空格/连字符/大小写）；不存在、已核销（返回原核销人时间）、已过期三类均拦截；核销记录核销人、时间、渠道与备注，状态机幂等防重复核销。
- **到期处理**：每个业务动作（`syncBusinessDay` 入口）与运营核销前先执行卡券到期扫描，已过到期时刻的待核销券批量流转为 `expired`（幂等，只处理仍可用券）；核销入口对漏网的到期券做二次拦截并补做到期。
- **对账 P6 与补券**：卡券账户按「有效券业务记录 ↔ 券实例」逐笔勾稽，并校验券码唯一、核销信息完整、到期状态一致。漏发可在运营复核后补发**新券**（新券码、有效期自补券日起算、带对账补券标记，append-only 不伪造历史），按业务记录幂等；孤立券/重复码等只标记人工核查，不自动作废。演示可在对账页注入「卡券漏发 1 张」走完整闭环。
- **同步与留痕**：券发放/预占/交付/核销/到期/补券同步更新卡券账户、券库存（P5）、业务记录与运营看板/角标，并写 append-only 卡券台账与全局操作记录；原始券实例与台账不裁剪、不改写。
- **演示数据**：预置今日一张待核销满减券（`CP-A1B2C-3D4E5`）、今日与 10 天前各一张已核销券、13 天前一张已过期券，以及一张风控已申诉、预占待交付的「视频月卡」。
- 逻辑冒烟测试：`npm run test:coupon`（覆盖正常发券/券码唯一/有效期、运营核销权限与重复/过期/不存在拦截、风控预占-放行交付-撤销释放、抽奖中券、到期扫描幂等、P6 检出/补发/再对账平账、库存与看板同步、台账留痕）。

## 风控申诉说明

- **可配置规则**（「🛡️ 风控申诉」运营视角配置，即时生效）：高价值奖品稀有度、当日抽奖频次、短时连抽/连兑窗口、高价值兑换积分阈值、用户黑名单、风控总开关
- **审核单状态机**：`待审核 pending → 已申诉 appealed → 已放行 released / 已撤销 revoked`，仅待处理态可申诉/审核，重复提交自动拦截
- **冻结语义**
  - 积分：抽奖/兑换成本即时从可用余额转入冻结；放行则核销为消费（积分奖品此时才入账），撤销则原路返还
  - 库存：奖品/商品 `remain -1` 同时 `frozen +1` 预占（不超卖）；放行核销预占，撤销回补
  - 限次：冻结抽奖占用每日/累计次数，撤销后返还
  - 卡券：券奖品/券商品冻结期仅预占库存、不发券；放行后发券交付（有效期自放行日起算），撤销释放预占、券始终不发出
- **权限**：用户仅能对本人单据申诉；仅运营可放行/撤销/配置规则（页内可切换演示视角）
- **审计**：冻结、申诉、放行、撤销、规则变更、视角切换全部写入操作记录；积分流水 append-only，业务记录与看板统计随审核结果同步
